0.1 Scope and non-goals

This manual covers the data plane of open-source Temporal: the protobuf schemas in temporalio/api, the server's internal persistence protos, the SQL and Cassandra table layouts, identifier and key derivation (shards, task queues, task IDs), the SDK payload conversion chain, and the gRPC surface. Operations topics such as Helm, metrics and dashboards appear only where they change bytes. Temporal Cloud internals are out of scope.

0.3 How the specimen was produced

  1. Built the server from source: go build ./cmd/server, 1.33.0.
  2. Started it with config/development-sqlite-file.yaml changed in two places: numHistoryShards: 4 and a file-backed databaseName. Registered namespace default with 72 h retention.
  3. Ran a Go worker (tools/probe/main.go in this repository) that registers OrderWorkflow(orderID). The workflow calls activity Charge(42), then workflow.Sleep(1s), then returns "order-1001:ok:42". A unary gRPC interceptor captured the protobuf body of every RPC.
  4. Read history_node, executions, shards, task_queues_v2 and timer_tasks directly out of the SQLite file.
  5. Decoded every blob with tools/annot. It walks bytes with protowire and resolves field names through the compiled protobuf descriptors of the server and API modules, so labels come from the real schema, not a hand-written one.

Only the bytes were captured, so timestamps belong to the capture run. Build IDs, the worker identity (14056@vm@) and UUIDs are real values from that run.

Chapter 1

1 Mental model

A workflow execution is an append-only event log plus a materialized projection of it. Workers never mutate state. They receive history, run deterministic code over it, and return commands. The server turns accepted commands into events.

2.2 History shards: the routing function

Every workflow execution belongs to exactly one history shard for its whole life. The mapping is a pure function of namespace ID and workflow ID. Run ID is not part of it, so all runs of a workflow ID share a shard, which is what makes current_executions a single-shard lookup.

// temporal/common/util.go:418–426
func WorkflowIDToHistoryShard(namespaceID string, workflowID string, numberOfShards int32) int32 {
	idBytes := []byte(namespaceID + "_" + workflowID)
	hash := farm.Fingerprint32(idBytes)
	return int32(hash%uint32(numberOfShards)) + 1 // ShardID starts with 1
}
Consequence numHistoryShards is an input to the hash. Changing it on a live cluster sends lookups for existing workflows to shards that do not hold them. Size it once. Cross-cluster replication between clusters with different shard counts goes through MapShardID (temporal/common/util.go:428–430), which panics unless one count is a multiple of the other (temporal/common/util.go:433–436).

2.3 Shard ownership, range IDs and task IDs

A shard is owned by one history host at a time. Ownership is represented by shards.range_id. Each acquisition increments it with a conditional write, and every later write to the shard's executions is conditioned on it. The range ID also partitions the 64-bit task-ID space:

3 Schema & nesting

All durable data is proto3. This chapter covers the wire rules that matter for Temporal's messages, the anatomy of HistoryEvent, and the recursive Payload containers, with byte-exact dumps of the first stored batch.

3.1 Wire rules that show up in Temporal bytes

Five encoder behaviors explain almost every surprise in a Temporal hex dump:

  1. Message fields have presence. A zero Duration that is set still costs 2 bytes (3a 00 = workflow_execution_timeout present, empty). The server sets many timeouts explicitly to zero, meaning "no timeout". Readers must distinguish unset from zero only for message-typed fields.
  2. Negative int64 costs 10 bytes. Timestamp.seconds is int64, not sint64. The specimen's workflow_run_expiration_time is Go's zero time.Time (0001-01-01T00:00:00Z = −62135596800 s). It encodes as an 11-byte field (08 + a 10-byte varint) inside a 14-byte submessage.
  3. Oneof arms are emitted last. protobuf-go marshals non-oneof fields before oneof fields (order.LegacyFieldOrder). So in event 11 the event-level user_metadata #301 comes before timer_started_event_attributes #20 (Fig. 15). Decoders must not assume ascending field order.
  4. Maps are repeated entries. map<string,bytes> is repeated {key=1; value=2}. Each entry costs a tag, a length and two inner tags: 4 bytes of framing before any content.
  5. Order is not canonical. Map iteration order is random unless deterministic marshaling is requested. Two replicas of the same state need not be byte-identical.

4 History batches & payload encodings

The event log is stored as a tree of branches made of transaction-sized nodes. User data inside those events is a Payload produced by the SDK's converter chain and optionally transformed by codecs. This chapter covers both on-disk "pages" and the value encodings inside them.

4.1 Trees, branches, tokens

History is stored as a tree so that reset and multi-cluster conflict resolution can fork it without copying. tree_id is the run ID of the run that created the tree. branch_id identifies one path. A forked branch records its ancestors as (branch_id, begin_node_id, end_node_id) ranges, so it can read shared prefixes from the parent branch.

message HistoryBranchRange{ string branch_id = 1; int64 begin_node_id = 2; int64 end_node_id = 3; }

A branch token is a serialized HistoryBranch. For the specimen it is 78 bytes: 0a 24 + 36-char tree ID + 12 24 + 36-char branch ID, with no ancestors. The same 78 bytes appear in WorkflowExecutionInfo.version_histories[].branch_token, in the retention timer task and in history_tree. The info string "<nsID>:<workflowID>:<runID>" exists so the garbage-collection scanner can find orphaned trees (temporal/common/persistence/data_interfaces.go:1431–1434).

4.2 Nodes: one row per transaction

Each call that appends events writes one history_node row per event batch. node_id is the first event ID of the batch. txn_id is a fresh shard task ID generated for the write (ms.shard.GenerateTaskIDs(len(newEventsBatches))). prev_txn_id links to the previous node's transaction, taken from executionInfo.LastFirstEventTxnId (temporal/service/history/workflow/mutable_state_impl.go:8585–8600).

Why negative On SQL the plugin stores txn_id multiplied by −1 (row.TxnID = -row.TxnID, temporal/common/persistence/sql/sqlplugin/sqlite/events.go:55–56). The ascending primary key (…, node_id, txn_id) then returns the newest transaction of each node first. This matches Cassandra's CLUSTERING ORDER BY (… txn_id DESC) without needing a descending index.

Batch boundaries are therefore transaction boundaries, not size-based pages. A batch has no size cap of its own. The per-event limits (limit.blobSize.*) and the per-execution totals (§8.1) bound it indirectly. The three-event node 6 shows how history can look out of order in time: event 6's event_time (+37.1 ms) is the real start time kept in mutable state, but the event was only written at completion (+41.6 ms).

4.3 Buffered events

While a WFT is in flight (between STARTED and COMPLETED), new external events such as signals, activity completions and timer firings cannot be appended. The history would otherwise contain events the worker never saw between STARTED and COMPLETED. They go to buffered_events (SQL) or WorkflowMutableState.buffered_events (#10) and are flushed into the next batch after COMPLETED. history.maximumBufferedEventsBatch = 100 caps the buffer (temporal/common/dynamicconfig/constants.go:2651–2653). Their placeholder ID is BufferedEventID = −123 until flush, and TransientEventID = −124 marks the activity-started placeholder seen in §1.4 (temporal/common/constants.go:19–24).

4.5 Codecs: transforming whole payloads

A PayloadCodec runs after conversion, on the client and worker only. The server never sees plaintext unless the codec emits it. The zlib reference codec marshals the entire input Payload, compresses it, and returns a new Payload with encoding=binary/zlib. It keeps the result only if it is smaller, unless AlwaysEncode is set (sdk-go/converter/codec.go:64–91). The specimen used AlwaysEncode on a 38-byte payload, which produced 52 bytes of zlib data and a 77-byte Payload, a 2× expansion. Small payloads do not compress, which is why the size check exists.

Encryption codecs follow the same shape: an opaque data plus metadata that names the scheme and key. For UI and CLI decoding, the SDK ships an HTTP handler that exposes codecs at POST …/encode and …/decode, carrying JSON-encoded Payloads (sdk-go/converter/codec.go:275–376). Search attributes are never passed through codecs, because the server must index them. The SDK serializes typed search attributes with converter.GetDefaultDataConverter(), bypassing the user's converter and codec (sdk-go/internal/internal_search_attributes.go:398–405).

Size accounting Server-side limits apply to the encoded payloads as the server receives them (§8.1). Compression helps you stay under limit.blobSize.error. Encryption usually adds overhead.

  • Numbers are never reused. ShardInfo carries reserved 4; 5; 8–12; 14–16 (temporal/proto/internal/temporal/server/api/persistence/v1/executions.proto:33–53). Old blobs with those numbers decode as unknown fields, which proto3 preserves and re-emits.

7.2 Framing on the wire

gRPC runs over HTTP/2. Each unary call is a HEADERS frame (:path = /temporal.api.workflowservice.v1.WorkflowService/StartWorkflowExecution, content-type: application/grpc, plus the Temporal metadata of §6.1) followed by DATA frames carrying one Length-Prefixed-Message: a 1-byte compressed flag, a 4-byte big-endian length, then the protobuf body. Temporal adds nothing to this envelope.

Size ceilings: the Go SDK's client accepts messages up to defaultMaxPayloadSize = 128 MiB (sdk-go/internal/grpc_dialer.go:56–57), and internode clients use the same 128 MiB (temporal/common/rpc/grpc.go:42–43). The binding limits are the per-payload and per-history limits of §8.1, which are far smaller.

7.3 Starting an execution

The response carries a Link.WorkflowEvent (#4 → #1) that points at (namespace, workflow_id, run_id, event_ref{event_id:1, event_type:STARTED}). Links are how Nexus and callbacks cross-reference executions. The same structure can be attached to events (HistoryEvent.links, #302).

7.4 Polling and the task token

Workers long-poll. The frontend holds a PollWorkflowTaskQueue open until matching supplies a task or the poll times out. After the first WFT, the specimen worker polled its sticky queue, which is private to the process and holds its cached workflow state:

The response bundles an opaque task_token, the execution, and history. For a non-sticky poll that is the full history. For a sticky poll it is only the events since the worker's last completed WFT.

The task token is a plain, unencrypted temporal.server.api.token.v1.Task (temporal/proto/internal/temporal/server/api/token/v1/message.proto:39–56). Treat it as opaque, but it is not secret: it names the namespace, execution and scheduling coordinates, and the server re-validates all of them against mutable state on respond. A stale token, one with the wrong scheduled_event_id, attempt or started_event_id, gets NotFound. clock is a vector clock (shard_id, task-ID clock, cluster_id) that lets history reject responses that arrive after a shard moved.

7.5 Completing a workflow task

Three fields in this request control what the server does next:

  • sticky_attributes (#4). The worker registers vm:bd9b0888-… with schedule_to_start_timeout = 5 s. Subsequent WFTs go to that queue (event 8's task_queue.kind = STICKY, Fig. 19). If the worker does not pick up a task within 5 s, the server reschedules it on the normal queue orders with full history.
  • request_eager_execution on the command. The worker asks for the activity task to be returned inline in the response instead of dispatched through matching. The specimen got it: the response below carries the activity task in activity_tasks, with started_time equal to event 6's timestamp. The concurrent PollActivityTaskQueue returned an empty response (0 B).
  • return_new_workflow_task (#5). This allows the server to return the next WFT inline if one is already due, saving a poll round-trip.

7.6 Reading history and results

A client waiting for a result does not page through the whole history. It long-polls with wait_new_event = true and history_event_filter_type = CLOSE_EVENT (2), and the server responds only once the close event exists. Full reads page by events with maximum_page_size. The frontend default is frontend.historyMaxPageSize = 256 (temporal/common/primitives/constants.go:21), and a next_page_token encodes the position. The response also has a raw_history form (repeated DataBlob) that returns stored batches without decoding. That is the SQL history_node.data of Chapter 4 passed through.

8.2 Run chains, resets and ID policies

  • Continue-as-new closes the run with WORKFLOW_EXECUTION_CONTINUED_AS_NEW (type 28, arm #33) naming new_execution_run_id, and atomically creates the next run with a new tree. The shard is unchanged, since routing ignores run_id. first_execution_run_id is carried forward, current_executions flips to the new run, and each run's history and limits start from zero.
  • Retry and cron create chains the same way. WorkflowExecutionStartedEventAttributes.attempt (#18, specimen 1) and first_workflow_task_backoff (#21) describe the new run.
  • Reset forks: the new run gets a new branch whose HistoryBranch.ancestors reference the old tree up to the reset point, so the shared prefix is not copied. auto_reset_points (WorkflowExecutionInfo #51, 92 B in the specimen) records candidate reset points per build ID.
  • ID policies gate reuse of a workflow ID. Reuse covers closed runs: ALLOW_DUPLICATE 1, ALLOW_DUPLICATE_FAILED_ONLY 2, REJECT_DUPLICATE 3, TERMINATE_IF_RUNNING 4 (deprecated). Conflict covers a running run: FAIL 1, USE_EXISTING 2, TERMINATE_EXISTING 3 (api/temporal/api/enums/v1/workflow.proto:17–46). Both are evaluated against the single current_executions row.

8.3 Updates and protocol messages

Workflow Update is carried as temporal.api.protocol.v1.Messages alongside commands. A COMMAND_TYPE_PROTOCOL_MESSAGE (14) command pins where each message falls relative to other commands, which is what SDK flag 3 enables. Only outcomes that matter for replay are persisted: ADMITTED (47 → arm #52), ACCEPTED (41 → #46) and COMPLETED (43 → #48). REJECTED (42) is never written. Updates that arrive with no other pending work may be delivered on a speculative WFT whose scheduled and started events are not persisted unless the WFT produces events. Its timeout runs on the in-memory timer queue (category 6). A rejected update therefore leaves no trace in history.

8.4 Nexus, callbacks and CHASM

Nexus operations add seven event types (48–54), plus 56 and 57 for cancel-request outcomes, and dispatch through the outbound task category (7, STATE_MACHINE_OUTBOUND), a queue separate from the transfer queue. Appendix D

D Glossary

Activity
Non-deterministic unit of work executed by a worker. Scheduled by command, retried by server policy.
Branch / tree
History storage topology: a tree per first run, branches per reset or conflict fork (§4.1).
Buffered event
External event held while a WFT is in flight, then flushed after completion (§4.3).
CHASM
The server's component-tree state framework. Archetype IDs are farm fingerprints of component names (§8.4).
Command
Worker → server instruction in a WFT completion (§1.3).
Current execution
The single open (or most recent) run for a workflow ID. Row in current_executions.
DataBlob
{encoding_type, data} wrapper for every persisted proto (§2.5).
Eager execution
Activity task (or first WFT) returned inline in an RPC response instead of via matching (§7.5).
Failover version
Per-event int64 encoding which cluster wrote it (§6.4).
Marker
MARKER_RECORDED event storing SDK-level non-determinism (version, side effects, local activities).
Mutable state
Materialized projection of history used for decisions (§5.1).
Namespace
Isolation and configuration unit. Name for clients, UUID internally.
Partition
Sub-queue of a task queue owned by one matching host. Default 4 (§5.4).
Payload
{metadata, data} carrier of every user value (§3.3).
Range ID
Shard or partition ownership epoch, used for fencing and task-ID ranges (§2.3).
Shard
Unit of history ownership and transactionality. fp32(nsID_wfID) mod N + 1.
Speculative WFT
WFT for an update, not persisted unless it produces events (§8.3).
Sticky queue
Worker-private queue host:uuid used while its cache holds the workflow (§7.5).
Task (history)
Outbox record in a shard queue category (§5.6).
Task token
Serialized token.v1.Task the worker echoes back on respond (§7.4).
Transient
Events not yet persisted: activity started (−124) or retried WFT events.
WFT
Workflow task: one round of "give the worker new history, get commands back".

A dense reference for engineers who already run Temporal and want the exact truth: which bytes a workflow execution becomes, where they are stored, how they are keyed, sharded, batched and versioned, and what travels on the wire. Each structure is traced to its .proto or Go source at a pinned commit. Each hex dump comes from a real run: one workflow (OrderWorkflow, 16 events) executed against a Temporal server built from source, with bytes read back from its SQLite file and captured from its gRPC calls.

Temporal has no single file format. It stacks protobuf messages in database blobs, gRPC frames and SDK payloads. These byte patterns identify each layer in a raw dump. All of them appear in the specimen.

0.1 Scope and non-goals

This manual covers the data plane of open-source Temporal: the protobuf schemas in temporalio/api, the server's internal persistence protos, the SQL and Cassandra table layouts, identifier and key derivation (shards, task queues, task IDs), the SDK payload conversion chain, and the gRPC surface. Operations topics such as Helm, metrics and dashboards appear only where they change bytes. Temporal Cloud internals are out of scope.

0.3 How the specimen was produced

  1. Built the server from source: go build ./cmd/server, 1.33.0.
  2. Started it with config/development-sqlite-file.yaml changed in two places: numHistoryShards: 4 and a file-backed databaseName. Registered namespace default with 72 h retention.
  3. Ran a Go worker (tools/probe/main.go in this repository) that registers OrderWorkflow(orderID). The workflow calls activity Charge(42), then workflow.Sleep(1s), then returns "order-1001:ok:42". A unary gRPC interceptor captured the protobuf body of every RPC.
  4. Read history_node, executions, shards, task_queues_v2 and timer_tasks directly out of the SQLite file.
  5. Decoded every blob with tools/annot. It walks bytes with protowire and resolves field names through the compiled protobuf descriptors of the server and API modules, so labels come from the real schema, not a hand-written one.

Only the bytes were captured, so timestamps belong to the capture run. Build IDs, the worker identity (14056@vm@) and UUIDs are real values from that run.

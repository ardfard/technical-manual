2 Physical layout

Where bytes live: four server roles, a fixed number of history shards, and a relational or wide-column store in which every stateful value is an opaque protobuf blob tagged with its encoding.

2.2 History shards: the routing function

Every workflow execution belongs to exactly one history shard for its whole life. The mapping is a pure function of namespace ID and workflow ID. Run ID is not part of it, so all runs of a workflow ID share a shard, which is what makes current_executions a single-shard lookup.

// {{T:common/util.go#L418-L426}}
func WorkflowIDToHistoryShard(namespaceID string, workflowID string, numberOfShards int32) int32 {
	idBytes := []byte(namespaceID + "_" + workflowID)
	hash := farm.Fingerprint32(idBytes)
	return int32(hash%uint32(numberOfShards)) + 1 // ShardID starts with 1
}
Consequence numHistoryShards is an input to the hash. Changing it on a live cluster sends lookups for existing workflows to shards that do not hold them. Size it once. Cross-cluster replication between clusters with different shard counts goes through MapShardID ({{T:common/util.go#L428-L430}}), which panics unless one count is a multiple of the other ({{T:common/util.go#L433-L436}}).

2.3 Shard ownership, range IDs and task IDs

A shard is owned by one history host at a time. Ownership is represented by shards.range_id. Each acquisition increments it with a conditional write, and every later write to the shard's executions is conditioned on it. The range ID also partitions the 64-bit task-ID space:

// {{T:service/history/shard/task_key_generator.go#L152-L153}}
a.nextTaskID         = rangeID << a.rangeSizeBits
a.exclusiveMaxTaskID = (rangeID + 1) << a.rangeSizeBits
// RangeSizeBits: 20, // 20 bits for sequencer   ({{T:service/history/configs/config.go#L562}})

2.4 Table catalog (SQL schema, SQLite v3 / version 0.11)

The SQL schemas for MySQL 8, PostgreSQL 12 and SQLite share one logical layout. Every stateful column is a MEDIUMBLOB or BYTEA paired with a VARCHAR(16) encoding column. The last column shows the row counts in the specimen after one workflow, including the two system workflows the server starts itself.

Task-table counts are a snapshot taken right after the run. Transfer and visibility tasks are range-deleted once their queue's ack level passes them, and a re-read a few minutes later found both tables empty. Timer tasks persist until they fire. The one remaining on shard 2 is the specimen's retention timer ([[fig:fig-timer1048618]]).

2.5 The DataBlob convention

The server never stores a bare proto. Everything goes through serialization.Encode, which returns a temporal.api.common.v1.DataBlob{encoding_type, data}. The two halves are written to the data and data_encoding columns.

// {{T:common/persistence/serialization/codec.go#L59-L102}} (abridged)
func Encode(m proto.Message, options ...EncodeOption) (*commonpb.DataBlob, error) {
	return encodeBlob(m, encodingTypeFromEnv(), options...)   // "" → ENCODING_TYPE_PROTO3
}
…
case enumspb.ENCODING_TYPE_PROTO3:
	data, err := proto.MarshalOptions{Deterministic: opts.deterministic}.Marshal(m)
	return &commonpb.DataBlob{EncodingType: enumspb.ENCODING_TYPE_PROTO3, Data: data}, nil
  • Encoding string on disk: EncodingType.String() from api-go's helper map, which gives "Proto3" (1) and "Json" (2). All specimen rows read Proto3.
  • JSON is selectable only through the test environment variable TEMPORAL_TEST_DATA_ENCODING ({{T:common/persistence/serialization/codec.go#L15-L39}}). Decoding supports both.
  • Determinism is opt-in (WithDeterministicProto3). By default map fields such as Payload.metadata and request_ids are marshaled in Go's map iteration order, so identical state can produce different bytes. Never compare persisted blobs byte for byte.

2.6 Cassandra: one table, many row kinds

On Cassandra, executions is a multiplexed table. The partition key is shard_id, and a type column discriminates shard, execution, transfer, timer, replication and visibility rows ({{T:schema/cassandra/temporal/schema.cql#L7-L9}}). Non-execution rows use fixed sentinel UUIDs in the namespace_id/workflow_id/run_id clustering columns. Nibble 3 of each sentinel encodes the row type:

timer task10000000-4000-f000-f000-00000000000020000000-4000-…30000000-4000-…
replication task10000000-5000-f000-f000-00000000000020000000-5000-…30000000-5000-…
visibility task / repl. DLQ10000000-6000-f000-f000-00000000000020000000-6000-…30000000-6000-…
generic history task10000000-8000-f000-f000-00000000000020000000-8000-…30000000-8000-…

Because every row of a shard shares one partition, a single BATCH … IF range_id = ? gives atomic, fenced writes across execution state and its tasks. Every mutation batch includes templateUpdateLeaseQuery, an UPDATE executions SET range_id = ? … IF range_id = ? on the shard row ({{T:common/persistence/cassandra/mutable_state_store.go#L22-L31}}, used at {{T:common/persistence/cassandra/mutable_state_store.go#L453}}). This is the Cassandra equivalent of the SQL transaction. history_node instead partitions by tree_id and clusters by (branch_id ASC, node_id ASC, txn_id DESC) ({{T:schema/cassandra/temporal/schema.cql#L58-L70}}), so the newest transaction for a node sorts first.

2.7 The only real file: the SQLite header

With the SQLite plugin a whole cluster is one file. Its first 100 bytes are the standard SQLite header. Decoding the specimen's header confirms WAL mode, which the config requests with journal_mode: wal, and 4 KiB pages.

Chapter 3

3 Schema & nesting

All durable data is proto3. This chapter covers the wire rules that matter for Temporal's messages, the anatomy of HistoryEvent, and the recursive Payload containers, with byte-exact dumps of the first stored batch.

3.1 Wire rules that show up in Temporal bytes

Five encoder behaviors explain almost every surprise in a Temporal hex dump:

  1. Message fields have presence. A zero Duration that is set still costs 2 bytes (3a 00 = workflow_execution_timeout present, empty). The server sets many timeouts explicitly to zero, meaning "no timeout". Readers must distinguish unset from zero only for message-typed fields.
  2. Negative int64 costs 10 bytes. Timestamp.seconds is int64, not sint64. The specimen's workflow_run_expiration_time is Go's zero time.Time (0001-01-01T00:00:00Z = −62135596800 s). It encodes as an 11-byte field (08 + a 10-byte varint) inside a 14-byte submessage.
  3. Oneof arms are emitted last. protobuf-go marshals non-oneof fields before oneof fields (order.LegacyFieldOrder). So in event 11 the event-level user_metadata #301 comes before timer_started_event_attributes #20 ([[fig:fig-event11timerstarted]]). Decoders must not assume ascending field order.
  4. Maps are repeated entries. map<string,bytes> is repeated {key=1; value=2}. Each entry costs a tag, a length and two inner tags: 4 bytes of framing before any content.
  5. Order is not canonical. Map iteration order is random unless deterministic marshaling is requested. Two replicas of the same state need not be byte-identical.

3.2 HistoryEvent anatomy

// {{API:temporal/api/history/v1/message.proto#L1188-L1220}} (comments stripped)
message HistoryEvent {
    int64 event_id = 1;                               // 1-based, dense, monotonically +1
    google.protobuf.Timestamp event_time = 2;
    temporal.api.enums.v1.EventType event_type = 3;
    int64 version = 4;                                // failover version (0 on local namespaces → omitted)
    int64 task_id = 5;                                // shard task-ID at write time
    bool worker_may_ignore = 300;
    temporal.api.sdk.v1.UserMetadata user_metadata = 301;
    repeated temporal.api.common.v1.Link links = 302;
    temporal.api.common.v1.Principal principal = 303;
    repeated temporal.api.sdk.v1.EventGroupMarker event_group_markers = 304;
    oneof attributes { … 60 arms, field numbers 6–65 … }
}

event_type and the populated oneof arm are redundant, and the server keeps them consistent. Two sequences of numbers are involved and they diverge. For event types 1–14 the arm is type + 5. From 15 onward the arms follow the historical declaration order of the attribute messages, not the enum. SDK decoders dispatch on event_type and never compute the field number.

Reserved oddities WORKFLOW_EXECUTION_UPDATE_ADMITTED = 47 is declared before ACCEPTED (41) in the enum file and uses arm #52. WORKFLOW_EXECUTION_UPDATE_REJECTED (42, arm #47) is documented as "never written to history" ({{API:temporal/api/enums/v1/event_type.proto#L139}}). Rejections travel only as protocol messages.

3.3 Payload, Payloads and the map containers

// {{API:temporal/api/common/v1/message.proto#L26-L61}}
message Payloads { repeated Payload payloads = 1; }
message Payload {
    map<string,bytes> metadata = 1;               // "encoding", "messageType", codec keys…
    bytes data = 2;
    repeated ExternalPayloadDetails external_payloads = 3;   // external storage references
}
message SearchAttributes { map<string, Payload> indexed_fields = 1; }
message Memo             { map<string, Payload> fields = 1; }
message Header           { map<string, Payload> fields = 1; }

Every user value that crosses the server is a Payload: workflow and activity inputs, results, signal arguments, memo and search-attribute values, header entries, failure details, and even timer summaries. The server treats data as opaque bytes and counts only sizes. It interprets metadata only for search attributes, where the type key selects the index column (the specimen's BuildIds SA carries type = KeywordList, see §5.5).

3.4 The first batch, byte by byte

Below is the complete data blob of the first history_node row: node_id 1, 259 bytes, event 1 (WorkflowExecutionStarted) and event 2 (WorkflowTaskScheduled). This is exactly what a reader of the SQL store sees. Trace task_queue (#5 → {name:"orders", kind:1}) and the empty timeout submessages.

The same event appears inside PollWorkflowTaskQueueResponse.history with identical bytes (213 B body). The server does not re-encode events for workers. GetWorkflowExecutionHistory also returns them unchanged: all 16 specimen events fetched through it, re-marshaled deterministically on the client, matched the stored history_node bodies byte for byte.

3.5 Attributes worth dissecting

Server-filled defaults: ActivityTaskScheduled

The worker's ScheduleActivityTaskCommandAttributes carried no retry policy ([[fig:fig-rpcrespondworkflowtaskcompleted]]). The event contains one anyway. The history service fills it from DefaultDefaultRetrySettings: initial interval 1 s, backoff 2.0, maximum interval 100 × initial, and maximum_attempts 0 (unlimited, therefore omitted) ({{T:common/retrypolicy/retry_policy.go#L77-L101}}). The coefficient is the only I64 field in the specimen: 11 00 00 00 00 00 00 00 40 is IEEE-754 2.0, little-endian.

Event-level metadata before the arm: TimerStarted

Default IDs are predicted event IDs. The Go SDK's commandsHelper.getNextID() returns the event ID that the resulting command will receive ({{SDK:internal/internal_command_state_machine.go#L1044-L1050}}). That is why timer_id is "11" and activity_id is "5", the IDs of the TimerStarted and ActivityTaskScheduled events. Replay depends on this prediction: a code change that inserts a command shifts every later default ID. The summary "Sleep" is a json/plain Payload in UserMetadata.summary. UIs render it, and replay ignores it.

SDK fingerprint in every completion: WorkflowTaskCompleted

sdk_metadata.lang_used_flags = [3] is packed (12 01 03). Flag 3 is SDKFlagProtocolMessageCommand ({{SDK:internal/internal_flags.go#L26}}). Once a flag is recorded in history, replays of that history must keep the flagged behavior even after an SDK upgrade (Chapter 6). worker_version.build_id defaults to the MD5 of the worker executable (SHA-256 under FIPS), which gives 32 hex chars ({{SDK:internal/checksum.go#L16-L50}}).

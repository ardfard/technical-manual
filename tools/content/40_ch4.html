Chapter 4

4 History batches & payload encodings

The event log is stored as a tree of branches made of transaction-sized nodes. User data inside those events is a Payload produced by the SDK's converter chain and optionally transformed by codecs. This chapter covers both on-disk "pages" and the value encodings inside them.

4.1 Trees, branches, tokens

History is stored as a tree so that reset and multi-cluster conflict resolution can fork it without copying. tree_id is the run ID of the run that created the tree. branch_id identifies one path. A forked branch records its ancestors as (branch_id, begin_node_id, end_node_id) ranges, so it can read shared prefixes from the parent branch.

// {{T:proto/internal/temporal/server/api/persistence/v1/history_tree.proto#L10-L35}}
message HistoryTreeInfo   { HistoryBranch branch_info = 1; Timestamp fork_time = 2; string info = 3; bytes branch_token = 4 [deprecated]; }
message HistoryBranch     { string tree_id = 1; string branch_id = 2; repeated HistoryBranchRange ancestors = 3; }
message HistoryBranchRange{ string branch_id = 1; int64 begin_node_id = 2; int64 end_node_id = 3; }

A branch token is a serialized HistoryBranch. For the specimen it is 78 bytes: 0a 24 + 36-char tree ID + 12 24 + 36-char branch ID, with no ancestors. The same 78 bytes appear in WorkflowExecutionInfo.version_histories[].branch_token, in the retention timer task and in history_tree. The info string "<nsID>:<workflowID>:<runID>" exists so the garbage-collection scanner can find orphaned trees ({{T:common/persistence/data_interfaces.go#L1431-L1434}}).

4.2 Nodes: one row per transaction

Each call that appends events writes one history_node row per event batch. node_id is the first event ID of the batch. txn_id is a fresh shard task ID generated for the write (ms.shard.GenerateTaskIDs(len(newEventsBatches))). prev_txn_id links to the previous node's transaction, taken from executionInfo.LastFirstEventTxnId ({{T:service/history/workflow/mutable_state_impl.go#L8585-L8600}}).

Why negative On SQL the plugin stores txn_id multiplied by −1 (row.TxnID = -row.TxnID, {{T:common/persistence/sql/sqlplugin/sqlite/events.go#L55-L56}}). The ascending primary key (…, node_id, txn_id) then returns the newest transaction of each node first. This matches Cassandra's CLUSTERING ORDER BY (… txn_id DESC) without needing a descending index.

Batch boundaries are therefore transaction boundaries, not size-based pages. A batch has no size cap of its own. The per-event limits (limit.blobSize.*) and the per-execution totals (§8.1) bound it indirectly. The three-event node 6 shows how history can look out of order in time: event 6's event_time (+37.1 ms) is the real start time kept in mutable state, but the event was only written at completion (+41.6 ms).

4.3 Buffered events

While a WFT is in flight (between STARTED and COMPLETED), new external events such as signals, activity completions and timer firings cannot be appended. The history would otherwise contain events the worker never saw between STARTED and COMPLETED. They go to buffered_events (SQL) or WorkflowMutableState.buffered_events (#10) and are flushed into the next batch after COMPLETED. history.maximumBufferedEventsBatch = 100 caps the buffer ({{T:common/dynamicconfig/constants.go#L2651-L2653}}). Their placeholder ID is BufferedEventID = −123 until flush, and TransientEventID = −124 marks the activity-started placeholder seen in §1.4 ({{T:common/constants.go#L19-L24}}).

4.4 Payload converters: the encoding matrix

The Go SDK's default DataConverter is a composite. It tries converters in a fixed order, and the first one that returns a non-nil payload wins ({{SDK:converter/composite_data_converter.go#L84-L102}}, order at {{SDK:converter/default_data_converter.go#L3-L16}}). 4.5 Codecs: transforming whole payloads

A PayloadCodec runs after conversion, on the client and worker only. The server never sees plaintext unless the codec emits it. The zlib reference codec marshals the entire input Payload, compresses it, and returns a new Payload with encoding=binary/zlib. It keeps the result only if it is smaller, unless AlwaysEncode is set ({{SDK:converter/codec.go#L64-L91}}). The specimen used AlwaysEncode on a 38-byte payload, which produced 52 bytes of zlib data and a 77-byte Payload, a 2× expansion. Small payloads do not compress, which is why the size check exists.

Encryption codecs follow the same shape: an opaque data plus metadata that names the scheme and key. For UI and CLI decoding, the SDK ships an HTTP handler that exposes codecs at POST …/encode and …/decode, carrying JSON-encoded Payloads ({{SDK:converter/codec.go#L275-L376}}). Search attributes are never passed through codecs, because the server must index them. The SDK serializes typed search attributes with converter.GetDefaultDataConverter(), bypassing the user's converter and codec ({{SDK:internal/internal_search_attributes.go#L398-L405}}).

Size accounting Server-side limits apply to the encoded payloads as the server receives them (§8.1). Compression helps you stay under limit.blobSize.error. Encryption usually adds overhead.

5 Mutable state, tasks & indexes

The metadata layer: the materialized per-execution record, the "current run" pointer, the version history, the task-queue keys that address matching's backlog, the visibility index, and the outbox of history tasks.

5.1 WorkflowExecutionInfo: the execution record

executions.data holds persistence.v1.WorkflowExecutionInfo, which has over 90 fields ({{T:proto/internal/temporal/server/api/persistence/v1/executions.proto#L56}}). A completed execution keeps only a few maps. Pending activities, timers and children live in the *_info_maps tables and are removed as they resolve, so all of those were empty for the specimen. 5.2 State, status and the current-run pointer

Two enums describe an execution, and they are orthogonal. State is the server-internal lifecycle ({{T:proto/internal/temporal/server/api/enums/v1/workflow.proto#L8-L14}}): CREATED 1, RUNNING 2, COMPLETED 3, ZOMBIE 4 (a replicated run that lost conflict resolution), VOID 5, CORRUPTED 6. Status is the public outcome ({{API:temporal/api/enums/v1/workflow.proto#L73-L82}}): RUNNING 1, COMPLETED 2, FAILED 3, CANCELED 4, TERMINATED 5, CONTINUED_AS_NEW 6, TIMED_OUT 7, PAUSED 8. A closed execution always has state 3. Status then tells how it closed.

current_executions is keyed without run_id, (shard_id, namespace_id, workflow_id). It stores the current run_id plus denormalized state/status/start_time columns (specimen: 3, 2, 2026-09-28 01:55:24.253) and the same WorkflowExecutionState blob. Start-workflow conflict checks (ID reuse and conflict policies) read this single row. The row survives closure, so the reuse policy can inspect the last run's status.

5.3 Version histories

version_histories records, per branch, the last event ID written under each failover version. The specimen has one branch and one item, {event_id: 16}. The version is 0 because the namespace is local, and proto3 omits 0. In a global namespace every failover appends an item such as (event_id, version). When clusters diverge, the lowest common ancestor of two version histories is where the branch forks during conflict resolution, which is why histories are trees.

version_histories {                               // WorkflowExecutionInfo #54 (87 B)
  histories[0] {
    branch_token: 0a 24 "01a0e5b9-57dd-72b4-…" 12 24 "01a0e5b9-57dd-7387-…"   // HistoryBranch
    items: [ { event_id: 16 /* version: 0 omitted */ } ]
  }
  // current_version_history_index: 0 omitted
}

5.4 Task-queue keys

Matching persists backlog and metadata per partition × type × subqueue. On SQL the key is a byte string built by taskQueueId() ({{T:common/persistence/sql/task_util.go#L53-L77}}), and its farm Fingerprint32 is the leading range_hash column, which shards rows across the key space:

The specimen namespace has 8 task_queues_v2 rows for orders, 4 partitions × 2 types. The partition count is matching.numTaskqueue{Read,Write}Partitions, default 4 (GlobalDefaultNumTaskQueuePartitions, {{T:common/dynamicconfig/shared_constants.go#L9}}). System queues are pinned to 1 ({{T:common/dynamicconfig/shared_constants.go#L11-L50}}). Pollers and adds are spread across partitions. Non-root partitions forward unmatched polls and tasks to their parent in a tree with up to matching.forwarderMaxChildrenPerNode = 20 children per node ({{T:common/dynamicconfig/constants.go#L1422-L1424}}), so a poll can match a task held by another partition.

tasks_v2 adds a pass column before task_id ({{T:schema/sqlite/v3/temporal/schema.sql#L114-L125}}). Tasks are read in (pass, task_id) order, where pass advances by stride scheduling per fairness key. Weighted fairness across tenants of one queue is therefore a property of the primary-key sort, not of an in-memory structure. The subqueue bit (0x80 in the type byte plus a varint subqueue ID) keeps priority levels in separate key ranges.

5.5 Visibility: the query index

5.6 History tasks: the outbox

6 Versions, determinism & writers

Several different things are versioned: the server binary, the SDK, the persistence schema, the protobuf contract, multi-cluster ownership (failover versions), and the workflow code itself. Each one leaves a distinct mark in the bytes.

6.1 Client ↔ server version negotiation

Every SDK call carries three gRPC metadata headers ({{SDK:internal/internal_utils.go#L21-L24}}):

headerspecimen valuechecked by
client-nametemporal-goserver: selects the supported range
client-version1.49.0server: must satisfy SupportedClients[client-name], else ClientVersionNotSupported
supported-server-versions>=1.0.0 <2.0.0server: its own ServerVersion (1.33.0) must fall inside

The server's table ({{T:common/headers/version_checker.go#L43-L52}}) accepts temporal-go, -java, -php, -typescript, temporal-cli and temporal-server below 2.0.0, and temporal-ui below 3.0.0. temporal-python is defined as a name but has no entry, so Python clients are not range-checked. Internode calls identify as temporal-server and advertise the feature list (follows-next-run-id). The namespace for routing and authorization travels in a temporal-namespace header as well as in the request body ({{SDK:internal/grpc_dialer.go#L66}}).

6.2 Schema versions

Each persistence backend carries its own schema version string, applied by temporal-sql-tool/temporal-cassandra-tool from schema/<db>/…/versioned/vX.Y/ manifests. At this commit SQLite is Version = "0.11" and visibility "0.1" ({{T:schema/sqlite/version.go#L3-L7}}). At startup the server checks the stored version with VerifyCompatibleVersion ({{T:common/persistence/schema/version.go#L10}}) and refuses a schema older than it expects. Because every row stores protobuf blobs, most feature work, which only adds proto fields, needs no DDL. Schema versions change only for new tables and columns, such as tasks_v2.pass for fairness or current_chasm_executions.

6.3 Proto evolution rules, as practiced

  • Numbers are never reused. ShardInfo carries reserved 4; 5; 8–12; 14–16 ({{T:proto/internal/temporal/server/api/persistence/v1/executions.proto#L33-L53}}). Old blobs with those numbers decode as unknown fields, which proto3 preserves and re-emits.
  • Enums keep dead values. WORKFLOW_ID_REUSE_POLICY_TERMINATE_IF_RUNNING = 4 [deprecated = true] ({{API:temporal/api/enums/v1/workflow.proto#L32}}), replaced by the separate conflict policy WORKFLOW_ID_CONFLICT_POLICY_TERMINATE_EXISTING = 3. CommandType skips 15.
  • Deprecated fields stay on the wire. HistoryTreeInfo.branch_token (#4) is [deprecated = true] yet still written: the specimen's history_tree blob spends 78 of its 255 bytes on it.
  • New cross-cutting fields go high. Event-level additions use 300+ (user_metadata 301, links 302, principal 303), leaving 6–299 for oneof arms.

6.4 Failover versions (multi-cluster)

For global namespaces every event and every mutable-state checkpoint carries a failover version (HistoryEvent.version #4, VersionHistoryItem.version). Each cluster owns one residue class modulo failoverVersionIncrement:

// {{T:common/cluster/metadata.go#L288-L309}}
next = current/increment*increment + initialFailoverVersion;  if next < current { next += increment }
IsVersionFromSameCluster(v1, v2) = (v1 - v2) % increment == 0

6.5 Workflow-code versioning and determinism markers

Replay is correct only if workflow code emits the same commands for the same history. The Go SDK records non-deterministic inputs as MARKER_RECORDED events. MarkerRecordedEventAttributes carries marker_name #1, a details map<string,Payloads> #2, workflow_task_completed_event_id #3, header #4 and failure #5 ({{API:temporal/api/history/v1/message.proto#L606-L616}}). The marker vocabulary is SDK-defined ({{SDK:internal/internal_command_state_machine.go#L231-L243}}):

Versionchange-id, version, version-search-attribute-updatedworkflow.GetVersion(changeID, min, max); no marker ⇒ DefaultVersion = -1 on replay ({{SDK:internal/workflow.go#L2413}})

GetVersion also upserts the TemporalChangeVersion search attribute (a KeywordList of fmt.Sprintf("%s-%v", changeID, version), {{SDK:internal/internal_event_handlers.go#L1059}}). Users may not set it themselves ({{SDK:internal/internal_event_handlers.go#L475-L476}}), and SDK flag 1 caps it at 2048 bytes.

6.6 Worker build IDs and deployments

Each WFT completion stamps the worker's build ID (worker_version.build_id in WorkflowTaskCompleted, worker_version_stamp in the request). The server folds these into the BuildIds search attribute as unversioned and unversioned:<build_id> for unversioned workers, which is how you query executions by the binary that ran them. use_workflow_build_id: true on ActivityTaskScheduled (#13) asks for activities to follow the workflow's build ID. Versioned workers (Worker Deployments) replace this with deployment and versioning_behavior fields and the TemporalWorkerDeploymentVersion SA (§5.5).

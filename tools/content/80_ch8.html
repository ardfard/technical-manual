Size checks for commands happen in the history service's WFT-completion handler ({{T:service/history/api/respondworkflowtaskcompleted/workflow_task_completed_handler.go#L515-L524}}). Oversized payloads call terminateWorkflow ({{T:service/history/api/respondworkflowtaskcompleted/workflow_task_completed_handler.go#L1591-L1603}}), because retrying the same deterministic code would reproduce them. Pending-count limits only fail the WFT, since the condition may clear. History-size and count enforcement is in {{T:service/history/workflow/context.go#L1471-L1525}}.

Headroom The specimen used 1541 B and 16 events for one activity and one timer, about 96 B per event. At that density the 51 200-event cap arrives long before 50 MiB. Payload-heavy workflows hit the size cap first. Continue-as-new at the suggest thresholds.

8.2 Run chains, resets and ID policies

  • Continue-as-new closes the run with WORKFLOW_EXECUTION_CONTINUED_AS_NEW (type 28, arm #33) naming new_execution_run_id, and atomically creates the next run with a new tree. The shard is unchanged, since routing ignores run_id. first_execution_run_id is carried forward, current_executions flips to the new run, and each run's history and limits start from zero.
  • Retry and cron create chains the same way. WorkflowExecutionStartedEventAttributes.attempt (#18, specimen 1) and first_workflow_task_backoff (#21) describe the new run.
  • Reset forks: the new run gets a new branch whose HistoryBranch.ancestors reference the old tree up to the reset point, so the shared prefix is not copied. auto_reset_points (WorkflowExecutionInfo #51, 92 B in the specimen) records candidate reset points per build ID.
  • ID policies gate reuse of a workflow ID. Reuse covers closed runs: ALLOW_DUPLICATE 1, ALLOW_DUPLICATE_FAILED_ONLY 2, REJECT_DUPLICATE 3, TERMINATE_IF_RUNNING 4 (deprecated). Conflict covers a running run: FAIL 1, USE_EXISTING 2, TERMINATE_EXISTING 3 ({{API:temporal/api/enums/v1/workflow.proto#L17-L46}}). Both are evaluated against the single current_executions row.

8.3 Updates and protocol messages

Workflow Update is carried as temporal.api.protocol.v1.Messages alongside commands. A COMMAND_TYPE_PROTOCOL_MESSAGE (14) command pins where each message falls relative to other commands, which is what SDK flag 3 enables. Only outcomes that matter for replay are persisted: ADMITTED (47 → arm #52), ACCEPTED (41 → #46) and COMPLETED (43 → #48). REJECTED (42) is never written. Updates that arrive with no other pending work may be delivered on a speculative WFT whose scheduled and started events are not persisted unless the WFT produces events. Its timeout runs on the in-memory timer queue (category 6). A rejected update therefore leaves no trace in history.

8.4 Nexus, callbacks and CHASM

Nexus operations add seven event types (48–54), plus 56 and 57 for cancel-request outcomes, and dispatch through the outbound task category (7, STATE_MACHINE_OUTBOUND), a queue separate from the transfer queue. Newer server subsystems are built on CHASM, a component tree persisted in chasm_node_maps and addressed by archetype_id. The specimen's retention timer already carries chasm_task_info.archetype_id = 2918170192 ([[fig:fig-timer1048618]]). At this commit a plain workflow is the root of a CHASM tree, and archetype IDs are farm.Fingerprint32 of a fully qualified component name, "<library>.<component>" ({{T:chasm/registrable_component.go#L220-L222}}, {{T:chasm/library.go#L58-L60}}). The workflow archetype is "workflow.workflow" ({{T:chasm/workflow.go#L4-L11}}), and recomputing fp32("workflow.workflow") gives exactly 2918170192. Standalone entities keyed by a business ID use current_chasm_executions (§2.4).

8.6 Archival

With archival enabled on a namespace, closing an execution schedules ARCHIVAL_ARCHIVE_EXECUTION (26) in the archival category (5). History is written to the configured URI (file://, s3://, gs://) as blobs, paged with FirstBlobPageToken = 1 / LastBlobNextPageToken = -1 ({{T:common/constants.go#L25-L28}}). The specimen's retention timer carries already_archived = true (#13), but that says nothing about archival state. The serializer hard-codes it to true "even though it's no longer checked in case someone downgrades" ({{T:common/persistence/serialization/task_serializers.go#L985-L987}}). It is a compatibility shim you will find in every retention timer.
